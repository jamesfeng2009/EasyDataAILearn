## 场景描述

**产品**：企业知识库大脑（Enterprise Knowledge Brain），多租户企业知识库 SaaS，基于自研 Agentic RAG（think → retrieve → tool_call → generate → reflect，max_iterations=5）。

**待评估的 AI 需求**：智能问答助手（`/chat` SSE 流式）——用户用自然语言提问，Agent 检索知识库、必要时调用 MCP 工具（OA 审批、IT 工单），返回带引用溯源的答案。

**为什么这个需求值得评估**：命中 Agent 三个甜区中的两个——
- 意图模糊：员工问"报销流程"可能是问标准、问入口、问审批人；
- 工具调用：`query_oa_approval`、`create_it_ticket` 等 7 个 MCP 工具（`app/mcp/server.py`）。

## 统计

| 指标 | 结果 |
|---|---|
| 答案数据**明确存在**（1-7） | **7 / 10** |
| 条件可用（存在性 OK，但线上灌库待验证） | 7 / 10 |
| 完全不存在但应拒绝（9） | 1 / 10 |
| 原始数据在、结论/工具缺失（8、10） | 2 / 10 |

## 结论：数据层达标，可以按 Workflow 起步；真正的瓶颈不在数据存在性

按 P1 判断标准，"超过一半找不到答案数据"才应暂停——本项目 7/10 明确存在，**未触及红线**。

但这次评估挖出三个比数字更有价值的发现：

### 发现一：项目自己就是"固定答案 FAQ 不需要 Agent"的活证据

`app/rag/faq_matcher.py:1-20` 明确写着：

```
TokenCache.get()  →  FAQMatcher.match()  →  HybridRetriever.search()
     (L1/L2)              (BM25 精准)            (向量+全文)
score 高于阈值时直接返回答案，跳过向量检索 + 重排 + 生成全链路。
收益：高频问答毫秒级响应（BM25 < 5ms vs 完整 RAG 链路 2-5s）；降低 LLM 调用成本
```

阈值 `_FAQ_SCORE_THRESHOLD = 15.0`（`faq_matcher.py:41`）。这正是 P1 第一部分"固定答案的 FAQ 不需要 Agent"的工程实现——意图确定、答案固定时，走 BM25 直出，不进 Agent Loop。**课程讲的原则，这个项目已经落地了。**

### 发现二："数据存在"要拆成两层验证

P1 说"数据在哪"，这个项目给了更精细的答案：

- **代码层存在**：40 篇种子文档 + 101 份测试文档 + 评测集，这是真的；
- **运行层存在**：未找到 dump 或已灌库证据，需要连库实测。

项目提供了增量保鲜机制：`content_hash`/`file_hash` 去重、`effective_from/to` 生效窗口、外部同步 `source_revision`（`models/knowledge.py:87-96,128-135,173-201`）。机制齐全，但"机制存在"不等于"数据已灌入"。**这是本次十问测试唯一没有完全闭合的地方，也是唯一需要实际动手验证的地方。**

### 发现三：真正缺数据的两题，恰好是 Agent 的高价值区

问题 8（归因）和问题 10（跨轮汇总 + 工具编排）答不出来，不是因为原始数据不在——`tickets`、`user_behaviors`、`messages`、`memory_facts` 都在——而是因为**"结论数据"和"编排工具"没建**。

这与 P1 的"有事实锚点 vs 无事实锚点"完全对应：问题 1-7 有锚点（文档原文），可以事实校验；问题 8 的"主要原因"是归因结论，无标准答案，需要先建小样本人工基线。

### 流程编排建议

项目已有完整 Agent Loop，但对首次上线仍建议按课程原则收敛：**FAQ/查数走快捷路径（已实现）→ 跨文档问答走 Workflow（检索 + 生成 + 引用）→ 归因与工具编排类问题最后开放，且保留人工审核**。这与项目已有的 `tool_approvals` / `DangerousToolGuard` 设计方向一致。

## 一句话

P1 在这个项目上不是用来"发现问题"的，而是用来验证它为什么能成——数据层做扎实了，Agent 才立得住。唯一没闭合的，是"线上到底灌没灌库"这件事，需要连库实测。
