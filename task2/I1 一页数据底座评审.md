## 第 3 步：一致性、写后可见性、权限、恢复要求

**一致性**
- 业务数据强一致（PostgreSQL 事务）；检索索引最终一致（Celery 异步构建）；
- 幂等写入：`doc_id + content_hash` 幂等，chunk.id 确定性生成（`docs/P1-reliability-data-consistency-design.md:489-511`）；
- 项目自己也承认"幂等写入基本缺失"是历史欠账，后来补齐——这正是 I1 讲的"AI 试写必须幂等"的真实代价。

**写后可见性**
- 文档发布 → 可检索之间有**秒级异步索引延迟**，不是写后即刻可见；
- 这是 I1 强调的"产品语义而非实现细节"：项目需要在 UI 显示"索引中"状态或提供 force-refresh，否则用户会遇到"刚上传就问、答不出来"。

**权限（这个项目做得最硬的地方）**
- RLS 行级隔离覆盖 **48 张租户表**，且已改成 **fail-closed**（`2026_11_10_1800-...rls_fail_closed.py`）：GUC 未设置时一行都看不见，避免 fail-open 导致的跨租户泄露；
- ABAC 密级过滤（public/internal/confidential/secret）**在重排之前**执行（`engine.py:20`，`docs/rag.md:105`）——这精确对应 I1 的"向量距离回答像不像，结构化条件回答能不能看"，而且**顺序是对的**：先挡住不能看的，再花钱重排；
- 工具调用有 `tool_approvals` + `DangerousToolGuard` 审批闸门。

**恢复**
- 备份：`BACKUP_CRON: "0 3 * * *"`，`RETENTION_DAYS: 14`，每周日 5:00 恢复演练（`docker-compose.yml:164-188`）；
- 索引可从 `documents`/`chunks` 重建（`rebuild_idempotency.py`、`backfill_*.py`）；
- 任务恢复：`agent_checkpoints` + `agent_event_logs` 混合恢复 + `task_outbox` 欠投递补投 + 死信队列。

## 第 4 步：统一数据库 vs 组合式架构

**结论：本项目是组合式架构（Polyglot Persistence），而且这是正确选择——不是统一数据库的失败案例。**

I1 课程说"中小规模、多类型数据、简化运维 → 统一数据库"。但这个项目给出了一个必须诚实面对的反例。它的理由不是"团队不会用统一库"，而是四条结构性约束：

| 判断依据 | 真实证据 |
|---|---|
| **检索范式异构** | 精确查询(PG) + 全文 BM25(OpenSearch) + 向量 k-NN(OpenSearch/Milvus/Qdrant) + 图多跳(Neo4j) + 缓存/锁(Redis)，单一数据库无法同时高性能覆盖 |
| **规模分层切换** | `< 500 万向量` 走 OpenSearch k-NN 共享集群，`> 500 万` 切 Milvus（`config.py:97-100`）——统一库无法弹性替换引擎 |
| **一致性模型不同** | 业务强一致、索引/记忆最终一致、任务用 Checkpoint/Outbox 补偿，强塞进单一强一致库会牺牲吞吐 |
| **复杂度已被抽象收敛** | `VectorStoreBase` + 工厂（`vector_store/base.py`, `factory.py`）使切换后端业务代码零改动——这正是组合式架构降低耦合的关键手段 |

**这与 I1 并不矛盾**：课程明确说"只有当独立系统带来的专业能力或规模收益大于同步与治理成本时，拆分才值得"，也说"已有成熟数据平台和可靠同步链路 → 延续组合式架构"。本项目两条都满足。

**真正要盯的风险**（不是架构选型，而是治理）：
- 索引与 DB 的一致性窗口（秒级）——需产品层明示；
- 48 张表 RLS fail-closed 对新表是"默认零防护"，必须用动态遍历 + 静态门禁测试纳入 CI；
- 记忆向量维度随部署模式变化（3072/1024），跨模式迁移需重算 embedding。

## 第 5 步：Agent 可写数据时的审批流程

这里要指出一个真实的差异：**项目没有数据库级 `FORK DATABASE` 分支，用的是"审批流 + 状态机 + 软删除 + superseded_by"实现同等的受控采纳**。这是工程上更常见的做法，也完全满足 I1 "隔离不等于自动合并"的原则。

项目已有的受控写入机制：

| 机制 | 实现 | 对应 I1 概念 |
|---|---|---|
| 审批闸门 | `knowledge_approvals`、`knowledge_conflicts`、`tool_approvals` | Merge 前的人工决策 |
| 状态机 | 约束规则 `pending_review → active → retired`；文档 `draft → pending_review → published → archived` | 试写 vs 正式采纳的隔离 |
| 冲突处理 | `memory_facts.superseded_by` / `verdict_reason` / `forgotten_reason` | 冲突策略 + 可遗忘可追踪 |
| 审计留痕 | `high_risk_audit_records`、`constraint_audit_records`、`agent_event_logs` | 记录任务、模型、提示词、差异 |

**建议的落地流程（贴合项目现状，不硬套 SQL 分支）**：

```text
1. 试写隔离：Agent 写入 draft/chunk_pending 状态，不直接改 published 文档
2. 差异暴露：knowledge_conflicts 记录新旧值冲突 + agent_event_logs 记录完整轨迹
3. 规则判定：低风险（记忆偏好更新）自动采纳；高风险（文档事实、审批结论）进 knowledge_approvals
4. 受控合并：人工/规则审批后切状态为 active/published，写入采纳人
5. 回滚兜底：软删除 deleted_at + superseded_by 链，保留历史版本可回溯
```

**冲突策略映射**：

| 数据类型 | 建议策略 | 理由 |
|---|---|---|
| 用户偏好记忆 | `THEIRS` | 用户最新表达优先，低风险可自动 |
| FAQ / 文档事实 | `FAIL` | 事实类冲突必须人工复核，否则幻觉会沉淀进知识库 |
| 约束规则 | `FAIL` | 项目已有 `pending_review → active` 状态机，天然适合卡住 |
| 审计/事件日志 | 不适用 | 只追加，不合并 |

## 一句话

I1 给了一个比课程模板更真实的答案：架构选型不看"哪个更先进"，看检索范式、规模分层和一致性模型——这个项目选组合式是对的，因为它的复杂度已经被 `VectorStoreBase` 抽象收敛了。而"隔离不等于自动合并"的原则，项目用审批流 + 状态机实现得比数据库分支更贴合工程实际。
